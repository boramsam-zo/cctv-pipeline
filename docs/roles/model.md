# 모델 — YOLO11s·X3D-S·Runpod 추론

## 2026-09-27 — 팀 시연을 위한 MLOps 최소 구성

MLOps는 모델 개발·검증·배포·운영을 반복 가능한 절차로 관리하는 일이다. 모델을 바꿔 실행하는 기능은 그중 배포·버전 관리에 해당한다. Pod/Serverless 선택이나 GPU 보유만으로 전체 절차가 완성되지는 않는다. [AWS MLOps 설명](https://aws.amazon.com/what-is/mlops/).

| 관리할 일 | 현재 도구를 이용한 최소 구성 | 남길 근거 |
|---|---|---|
| 학습·실험 | Colab 코드와 Git 버전, 기존 실행 결과 기록 | 데이터 목록·라벨/분할·학습 설정·seed·실제 출력 |
| 배포 전 검증 | 고정된 검증 목록에서 기존/새 후보 비교, 같은 평가 조건 확인 | 미탐/오탐·미분류·속도·메모리, 조건이 다르면 차이 |
| 모델 등록 | S3의 버전별 가중치·전처리/클래스/임계값 명세와 해시, JSON 또는 DB의 등록 목록 | 코드/환경·평가 근거·모델 버전·분석 프로필 ID |
| 배포·실행 | 선택한 버전을 Runpod에 준비하고 실제 로딩/입출력 확인, BE는 등록 프로필로 요청 | 배포 버전·검증 결과·job/run별 고정 프로필 |
| 운영 확인·복귀 | 작업 로그·지연·실패·검토 결과 수집, 문제 시 이전 배포/프로필로 복귀 | 결과와 사용 버전 연결, 원본 결과/이전 버전 보존 |

등록 목록은 어느 가중치·코드·설정이 하나의 실행 버전인지 연결하는 역할이다. 첫 시연에는 Git+S3+작은 manifest/DB 목록으로 설계할 수 있고, 전용 실험 추적/모델 등록 도구 도입은 이후 필요에 따라 검토한다. S3 모델 등록·버전 전환·복귀가 현재 구현됐다는 뜻은 아니다. 현재 확인한 S3 연결은 결과 보관이며 실제 구현 상태는 재개 요약을 따른다.

### 모델을 바꾸는 예

동일 구조의 X3D-S v1이 실행 중일 때 v2를 별도 경로에 등록하고, 같은 검증 목록에서 기능·품질·자원 조건을 확인한다. 채택한 뒤 **새 작업부터 v2를 사용하고 이미 접수한 작업은 지정된 v1으로 끝내는 방식**을 제안한다. 문제 발생 시 이후 작업의 기본 버전을 v1으로 되돌린다. 단일 Pod의 중지/재시작 배포라면 진행 작업을 끝낸 뒤 전환하거나 명시적으로 실패·재시도 처리해야 하며 무중단 전환을 보장하지 않는다. 가중치 파일을 실행 중인 경로에 덮어써 버전을 섞지 않는다.

X3D-S에서 R3D-18/R(2+1)D로 구조까지 바꾸면 로더·입력 크기·샘플링·정규화·출력 해석을 모델별로 맞춰야 한다. FE/BE에는 공통 결과 계약으로 연결한다. 현재 `analysis_profile_id`는 이를 기록하기 위한 설계이며 받은 X3D용 `.pt` 경로만 다른 모델 파일로 바꾸는 기능은 아니다. 새 운영 모델을 선택하거나 교체하지 않았다.

자동 재학습은 후속 자동화 항목이다. 첫 단계는 사람이 검토한 새 자료로 실험하고, 평가 기준을 통과한 버전을 선택해 배포하는 관리 절차부터 구성한다. 운영 피드백은 검토·라벨 기준을 거쳐 사용하며 최종평가 자료를 자동 학습에 넣지 않는다. 실제 오탐/미탐은 정답이 확인된 범위에서만 집계한다. 프롬프트·VLM/임베딩 모델·문서 모음·검색 설정 버전도 결과와 연결해 원인을 추적한다.

**현재 제안하는 다음 관리 항목은 한 분석 프로필의 가중치·코드·전처리·평가 근거 연결과 job 결과의 버전 기록이다.** 새 설치·클라우드 자원·학습·모델 교체는 이 문서 변경에 포함하지 않는다.


2026-09-27 현재 실행 환경은 Runpod A4000 Pod다. 사용자 한 건의 결과5파일을 받아 해시·창/후보 재계산·handoff 일치 등30검사를 통과했다. 8.6초 영상의8창/양성6→후보1개(2.0–8.6초, 대표3.0초), 해당장면Car박스3개다. 박스IoU0.411–0.692로 중복 여부/실제차량수는 원본 대조가 필요하다. PyTorch피크예약420MiB는 이번 실행의 할당기 수치이며 장치전체/긴영상 요구량을 뜻하지 않는다. [결과 검증](../../artifacts/runpod/a4000-20260927-01/received/fd20cca0be53483696e6704e7c985b84/verification.json)·[현재 인프라/인수인계](infrastructure.md)·[Runpod API 계약](../contracts/service_contract.md)을 우선한다. 이 문서의 Modal 함수 관련 설명은 이전 배포안이며 모델 역할·평가 원칙은 유지한다.

기준: [PRD](../../PROJECT_BRIEF.md) · [공통 계약](../contracts/service_contract.md). **서비스 선택은 YOLO11s + X3D-S다.** 선택한 이름과 실제 확보·검증된 가중치를 구분한다. 기존 R3D-18 결과는 비교 이력이며 이 구성의 성능 증거로 옮기지 않는다.

## 책임과 처리 흐름

S3 원본+분석 프로필→원본 PTS와 X3D-S 전처리→창별 점수·후보 정리→후보 원본 장면의 YOLO 객체 정보→클립·프레임·결과 manifest→S3 저장과 완료 반환.

사용자 확정 목적은 X3D-S의 사고 후보 구간 판별과 YOLO의 사고 영상 객체 정보 제공이다. 이를 반영해 X3D-S로 후보를 찾은 뒤 해당 원본 장면에 YOLO를 순차 실행하는 방식을 제안한다. YOLO crop/특징을 X3D-S에 입력하지 않는다. 후보가 없으면 YOLO를 skipped/no_candidates로 남긴다. 후보 전후 어느 범위·몇 프레임에서 객체를 찾을지는 근거 프로필에 기록한다.

## 모델 프로필에 반드시 적을 항목

| YOLO11s | X3D-S | 공통 |
|---|---|---|
| 확인한 7개 class ID/name, 원래 클래스와의 매핑, confidence/NMS 설정, 입력 크기, 좌표 복원 | 학습된 사고 분류 가중치, 클래스 순서, 프레임 수/간격·crop·정규화, 창 길이/간격, 판정 규칙 | weights SHA256, 코드/패키지 버전, 모델 출처·사용 조건, 입력 품질 기준, GPU 종류, 측정 범위 |

사용자가 지정한 deployment_handoff의 두 가중치와 코드를 확인했다. 파일 11개가 동봉 manifest의 크기·SHA256과 일치하며 YOLO .pt의 클래스 7개를 정적 확인했다. Dynamic의 뜻은 미확인이다. [접수 근거](../contracts/received-model-metadata-v0.2.json)와 공통 계약의 클래스 맵을 따른다. 일반 객체/행동 사전학습 모델을 사고 모델로 표시하지 않는다. 기존 R3D의 설정을 X3D에 복사하지 않는다.

## 수신 코드에서 확인한 설정과 추가 연결

- YOLO 파일: `yolo11s_accident_150_e30_best.pt`, SHA256 `44f7e937068ec8862e30245314ec1cd54d6782e716eec1abc3fcf3ab7b761007`. 입력 640, confidence 0.25, 후보 시각 **한 프레임** 객체 탐지. 30epoch는 전달 README 설명이며 체크포인트 최상위 epoch 값은 -1이다.
- X3D 파일: `x3d_s_real_so_tad_epoch7_best_model.pt`, SHA256 `ca2db4a25c9cd2d859a7143932d911a3351beacc5193de3ada16f3115bea09bf`. 체크포인트 epoch 7·threshold 0.5를 정적 확인했다.
- 전달 코드: RGB 182×182, 2초 창·16장·1초 이동, uint8/255 후 mean 0.45/std 0.225, Normal=0/Collision=1(전달 설명 기준), 양성 기준 ≥0.5. 연속 양성 창을 묶고 음성 창에서 끊는다. 첫 양성 창 중간을 후보 시각, 창 끝을 최초 관측 가능 시각으로 기록한다.
- `pipeline.py`는 최대 120초 상한과 전체 축소 프레임 적재를 사용한다. 프레임 인덱스/FPS로 시간을 계산하고 짧은 영상에서는 샘플 인덱스를 clamp하므로, 기존 저장소의 실제 PTS·서로 다른 프레임·미분류 정책과 차이가 있다. 120초는 받은 코드의 상한이며 새 서비스 운영 합격 기준이 아니다.
- `streaming.py`는 프레임 수신용 후보 emitter다. 후보 한 프레임의 실제 입력 시각을 별도 필드로 반환한다. RTSP 수신·서버 버퍼·S3·Modal·VLM 전송 자체는 포함하지 않는다.
- 실제 PTS와 샘플 품질 검증, 실패/미분류 coverage, 근거 클립·프레임 생성, 계약 어댑터, 클라우드 연결을 추가해야 한다. 기존 평가 재현 프로필과 이 보완을 넣은 서비스 프로필을 버전으로 나누고 전후 비교한다.
- 전달 README의 SO-TAD400 성능·보류79 설명은 제공자 보고다. 이번에는 평가 목록·예측을 받거나 성능을 재계산하지 않았다. 기존 팀의 SO-TAD479/400 비교와 혼동하지 않는다.

## 시간·후처리·근거

- 모델은 입력 창의 점수를 출력하고 파이프라인이 창 시각을 붙인다. 원본 시각·판정에 사용한 마지막 프레임·실행 경과시간을 나눈다.
- 입력 구간 선택에 정답 사고시각/유형/파일명 정보를 사용하지 않는다.
- 후보 병합의 임계값·연속 조건·병합 간격·짧은 후보 처리·중복 기준은 candidate_policy_version으로 고정한다. 정확한 값은 평가 전 확정한다.
- 미분류 창과 분석하지 못한 범위를 보존한다. 예측 창 수+미분류+남은 창 수가 계획과 맞아야 한다.
- 클립은 원본 기준 시작/끝과 해시를 남기고 대표 프레임마다 원본 시각을 넣는다. 검토용 후행 프레임 사용은 탐지 당시 사용 프레임과 구분한다.
- YOLO 박스는 원본 크기에 복원한 뒤 정규화한다. 박스 수를 사고 차량 수로 확정하지 않는다. 추적기를 추가하지 않은 상태에서 지속 track_id를 보장하지 않는다.

## Modal 함수의 경계

입력은 공통 계약의 작업 입력, 출력은 S3 manifest 위치·해시다. GPU 단계는 근거 저장까지 담당하고 외부 VLM 응답 대기는 BE로 넘긴다. 모델 로딩 실패·디코딩 실패·OOM·timeout을 단계별 오류로 구분한다. 재시도 산출물은 run/attempt 경로에 분리하고 원본·이전 결과를 덮어쓰지 않는다.

BE가 상태를 회수할 수 있도록 실제 시작/끝, 처리 창 수, 주요 단계 시간과 job/run ID를 로그·manifest에 기록한다. GPU 동시 실행 수·메모리·모델 동시 적재 가능성은 측정 전 미확인이다.

## 기존 코드에서 참고할 것

저장소의 `src/boram3_cctv/video_inference.py`는 원본 시각·시간순 창 선택의 참고다. `scripts/analyze_video.py`는 기존 R3D 점수 생성 경로다. `src/boram3_cctv/events.py`는 합성 시험 목적 제한이 있으므로 그대로 실제 모델 결과에 붙여 완료됐다고 표시하지 않는다. 새 어댑터·후처리 연결은 별도 구현과 검증이 필요하다.

## 첫 작업과 완료 기준

첫 작업은 받은 코드의 결과를 서비스 계약으로 변환하고 실제 PTS·coverage·근거 파일 생성의 차이를 정리하는 것이다. 모델 연산이 필요하면 대상·시간·비용 범위를 정한 실행으로 구분한다.

기능 기준: 실제 입력 근거와 창 시각 일치, 클래스/좌표/모델 버전 검증, 후보/미분류 보존, 재시도 결과 중복 방지. 품질 기준: 동일 평가 목록·정답으로 미탐/오탐·미분류를 함께 측정. 운영 수치 합격선은 미정이며 시연 성공만으로 운영 합격을 선언하지 않는다.
